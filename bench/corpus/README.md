# sqlite-query-corpus

Real queries from popular SQLite applications, with schemas and synthetic data so every query runs. It's for
benchmarking and correctness-testing `cursed-sqlite-turbo`. Ranking and the survey are in [INDEX.md](INDEX.md) and
[SURVEY.md](SURVEY.md). Nothing here is benchmarked; that's another session's job.

```bash
python3 tools/run.py --all                 # build each project's DB, run every query, print row counts
python3 tools/run.py memos signal          # just these projects
python3 tools/run.py --all --scale 4       # 4x the synthetic data
python3 tools/run.py --all --record --manifest   # refresh expected.json files and manifest.jsonl
python3 tools/time.py --all                # indicative stock timings -> projects/*/timings.json
python3 tools/index.py                     # rescore; regenerates STATS.md and scores.json, prints the INDEX table
tools/fetch.sh memos                       # pinned download of the original source files, into fetched/ (gitignored)
```

The runner only needs the `sqlite3` CLI (set `$SQLITE3` to use another build, e.g. a turbo-enabled shell). A few Anki queries use `REGEXP`, which the stock shell provides through its built-in regexp extension, not core SQLite; a custom shell needs the same. Each
query runs in its own CLI process inside `BEGIN … ROLLBACK`, so writes don't leak. The CLI runs with `TZ=UTC`, so `'localtime'` date maths is reproducible.

## Layout

```
projects/<slug>/
  meta.json      provenance and scores (below)
  schema.sql     DDL the queries need, from the project's migrations or schema file
  data.sql       deterministic synthetic data in plain SQL; reads temp table _cfg(scale), default 1
  queries.sql    the queries, one annotated block each (below)
  expected.json  written by run.py --record: rows/changes, output hash, EXPLAIN QUERY PLAN, VDBE op count, tags
  timings.json   written by tools/time.py: indicative stock wall time per query (triage, not benchmarking)
manifest.jsonl   one line per query across all projects (generated by run.py --manifest)
STATS.md         tag distribution, complexity tables, best targets (generated by tools/index.py)
scores.json      per-project interest/visibility scores (generated by tools/index.py)
INDEX.md         ranking, scoring explanation, top 10, specialiser targets
SURVEY.md        every candidate considered, with reasons
tools/run.py     runner + manifest builder
tools/index.py   scoring and STATS.md
tools/time.py    indicative stock timings (min of 3, one CLI process) for the CPU-bound table in STATS.md
tools/fetch.sh   fetches meta.json's fetch_paths at the pinned SHA
```

### queries.sql

```sql
-- @id memos.list_memos.home_feed            unique, <project>.<area>.<what>
-- @src store/db/sqlite/memo.go:118-246      path:line or path:start-end at the pinned SHA
-- @style ? positional, dynamic WHERE        the app's original binding style and how the text was built
-- @tags hotpath,dynamic                     manual tags only; the runner adds the automatic ones
-- @note one line on why it's interesting
-- @modified what was changed and why        only when the text differs from the app's beyond normalisation
-- @param ?1 7                               one per bind parameter: name, then an SQL literal
SELECT ...;
```

**Normalisation:** whitespace is reflowed and app-side string building is resolved into one representative
instantiation. Bind parameters become `?N` (positional apps) or keep their names (`:name`, `$name`, `@name`). Identifiers
and SQL keywords are left as the app wrote them.

**Manual tags:**

| Tag | Meaning |
|---|---|
| `hot-small` | a very hot, cheap statement (point lookup, short insert). The guard against regressions |
| `hotpath` | runs on a hot user path (list page, sync, search, dashboard), as opposed to admin or maintenance |
| `dynamic` | the app builds the text at runtime; this is one instantiation |
| `expect-empty` | returning 0 rows is correct for this data |
| `wallclock` | the result depends on the current time or `random()` (also set automatically when the SQL, a parameter value, a view it reads, or the project's data recipe uses `'now'`, `'localtime'`, a zero-argument date function such as `datetime()`, `CURRENT_*` or `random()`). Compare row counts, not hashes, across days |
| `batch` | a batched write (multi-row VALUES, INSERT … SELECT) |
| `analytics` | a dashboard, report or statistics aggregate |
| `heavy` | set by the manifest when the indicative stock time at scale 1 is 1 s or more. Exclude these for quick benchmark rounds |
| `cpu-evidence` | directly implicated by a public slowness report; the issue URL is in `@note` and in meta.json's `cpu_evidence` |
| `modified` | set automatically when `@modified` is present |

**Automatic tags** (`run.py`, from the SQL text and `EXPLAIN QUERY PLAN`):

| Kind | Tags |
|---|---|
| Statement kind | `read`, `insert`, `update`, `delete`, `replace` |
| Structure | `join`, `join3` (3 or more table accesses in the plan), `subquery`, `correlated`, `cte`, `recursive-cte`, `window`, `compound` |
| Grouping and ordering | `groupby`, `having`, `aggregate`, `distinct`, `topn` (ORDER BY + LIMIT), `orderby`, `offset` |
| Predicates | `exists`, `in-list`, `in-subquery`, `like`, `glob`, `regexp`, `fts`, `json`, `case`, `string`, `date`, `collate` |
| Writes | `upsert`, `insert-ignore`, `returning` |
| Plan features | `temp-btree`, `auto-index`, `multi-index-or`, `full-scan`, `vtab` |

### data.sql rules

- **Plain SQL, no `random()`:** values come from hashes of a row counter, like `(i * 2654435761) % 4294967296`. Take
  different columns from different bits (`(h / 1024) % 5`), or they correlate and filters come back empty.
- **Scale:** row counts multiply by `(SELECT scale FROM _cfg)`. Scale 1 should build in a few seconds, and the database
  should stay under about 100 MB.
- **Realistic shape:** distributions follow the app (a few heavy users, most rows recent, realistic JSON payloads), and
  every query returns rows unless it's tagged `expect-empty`.
